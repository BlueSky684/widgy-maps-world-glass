# Automatic flight presentation

Clients opt in with `flight_mode=auto-v1` alongside `presentation=agenda-v2` or `metadata=native-v1`. The shared `context=home-v1` URL forwards the mode. Older clients and explicit legacy profiles retain their contract.

The resolver recognizes conventional English/Hebrew flight destinations, explicit origin/destination titles and IATA routes such as `JFK → LHR`, including prefixed or parenthesized flight numbers. A destination-only title uses the event location as departure. It never uses the phone or calendar time zone as an airport location. It does not perform flight-number lookups, read email, or change calendar events.

IATA airport codes take priority. Full airport names and city names resolve only to an unambiguous IANA zone. Closed airports are excluded from the generated lookup. A city with multiple airports in the same zone retains its city label; cities in different zones require a country or airport code. Missing or ambiguous endpoints keep a flight card but show an em dash for the unknown local time. Arbitrary event titles with no recognizable flight/route structure remain ordinary events. The widget requires matching server metadata to enable flight enrichment; native agenda data remains the fallback when metadata is unavailable.

Calendar instants remain authoritative. Conversion uses the departure zone for start and arrival zone for end, with date-aware DST rules. Arrival labels show the civil-date difference, including negative or +2 day changes across the date line. This is scheduled calendar data, not live airline status. Every date and flight number is processed afresh; the widget contains no flight-specific profiles.

`flightEvidence` binds the output to both absolute event instants. With `context=home-v1&native=v2`, the shared handler matches the supplied native date, row titles/locations/clocks and count, then validates unique event identity, zones, calculated endpoint times and arrival-day labels on the server. `lib/calendar-bridge/native-calendar.cjs` is shared by production and tests. This avoids requiring Intl in Widgy or chaining JavaScript variables.

The native inputs are `native_date`, `native_count`, `native_hour`, `native_minute`, and `n1_title`/`n1_location`/`n1_start`/`n1_end` through row 4. The existing `day_zone` supplies the device zone. Each comes from an independent native data source using URL-safe literal replacements, rather than JavaScript interpolation. The private client reads each `calendar.native.fields.calendar_event_N_*` scalar directly from the same JSON URL, plus `spacious` and `bundle`. No calendar item is joined by index alone. All original native text layers, flight icons/dividers, positions and visibility predicates remain in the private export.

The projection is returned even on calendar metadata failure, with native fallback fields and a bounded status. It is never persisted in a shared cache or forwarded to weather/location handlers. No title, location, input query or projected values are logged. `X-Widget-Native-Status` and bounded `nativeStatus` logs distinguish `flight-matched`, `native-fallback`, `invalid-native-input` and `metadata-unavailable`. A full transport failure still requires the device to fall back; physical rendering and URL substitution remain device acceptance checks.

Run `node --test tools/test-native-projection.mjs tools/test-calendar-auto-flights.mjs tools/test-calendar-agenda-v2.mjs tools/test-calendar-source-timezones.mjs tools/test-widget-context.mjs tools/test-calendar-resilient-handler.mjs tools/test-calendar-resilient.mjs`. Private export tests additionally require zero JavaScript variable chains, unchanged flight geometry, exact scalar paths, hostile-text URL round trips, and reproduce the old missing-variable/Intl failures. Those tests do not establish physical iPhone rendering.

Airport data sources, hashes and license are in `airport-data-notice.txt`. No calendar token, event or personal itinerary is stored in the lookup or the public tests.
